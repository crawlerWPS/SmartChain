## 2. 产品背景与目标

### 2.1 业务背景

供应链金融业务中，贸易背景的真实性核验是风控的核心环节。目前存在以下痛点：

- **核验手段分散**：各业务线（保理、应收账款质押、订单融资等）独立开展贸易背景核验，缺乏统一的服务能力，导致重复建设和标准不统一。
- **人工核验效率低**：大量依赖人工审核单据、电话核实等方式，处理周期长、成本高，且核验标准因人而异。
- **欺诈风险突出**：虚假贸易合同、伪造发票、虚构应收账款等欺诈行为频发，传统核验手段难以有效识别新型欺诈模式。
- **数据孤岛严重**：税局、工商、物流、征信等外部数据源分散，未形成体系化的数据调用和交叉验证能力。
- **核验记录追溯难**：核验过程缺乏标准化记录，审计和合规追溯困难。

### 2.2 业务目标

| 目标编号   | 目标描述               | 衡量指标        | 目标值                   |
| ------ | ------------------ | ----------- | --------------------- |
| OBJ-01 | 建立统一的贸易背景真实性核验服务能力 | 覆盖供应链金融产品种类 | 覆盖保理、应收账款质押、订单融资等全部产品 |
| OBJ-02 | 提升核验效率             | 单笔核验端到端处理时间 | <30秒                  |
| OBJ-03 | 提高欺诈检出能力           | 欺诈检出率       | >95%                  |
| OBJ-04 | 降低误报率              | 误报率         | <5%                   |
| OBJ-05 | 实现核验标准化            | 核验规则统一率     | 100%                  |
| OBJ-06 | 建立完整的核验审计追溯体系      | 核验记录完整率     | 100%                  |

### 2.3 适用范围

本产品作为供应链金融业务中台能力，为以下业务场景提供统一的贸易背景真实性核验服务：

- 保理业务（国内有追保理（批量反保理、保理池、租赁保理）、国内无追保理）
- 应收账款质押融资
- 订单融资（基于采购订单的融资）
- 存货融资（基于仓单的融资）

## 3. 产品概述

### 3.1 产品定位

**产品名称**：真实性核验助手 (Authenticity Verification Assistant, AVA)

**产品定位**：供应链金融业务中台的核心能力组件，为保理、应收账款质押、订单融资等供应链金融产品提供统一的、标准化的、智能化的贸易背景真实性核验服务。

**系统边界**：

- 本系统作为中台能力，对外提供标准化核验服务API
- 各前端业务系统通过API调用本系统完成核验任务
- 本系统不直接处理融资审批、放款等核心资金业务
- 本系统不直接管理客户信息，但会调用客户信息用于核验

### 3.2 核心价值主张

| 价值维度    | 价值描述                               |
| ------- | ---------------------------------- |
| **统一化** | 构建统一的核验服务能力，消除各业务线独立建设导致的重复投入和标准差异 |
| **自动化** | 通过规则引擎和智能模型，实现核验流程自动化，大幅降低人工处理成本   |
| **智能化** | 分阶段引入机器学习和关联图谱分析，持续提升核验准确率和欺诈检出能力  |
| **可追溯** | 全流程核验记录留痕，满足审计合规要求，支持核验结果追溯和争议处理   |
| **可扩展** | 开放式架构设计，支持灵活接入新的数据源和核验规则           |

### 4.2 用户场景分析

#### 场景一：融资申请发起核验

| 项目   | 内容                                                                                                      |
| ---- | ------------------------------------------------------------------------------------------------------- |
| 角色   | 客户经理 (R-04)                                                                                             |
| 触发条件 | 客户提交融资申请后，需对贸易背景进行核验                                                                                    |
| 前置条件 | 客户已提交融资申请及贸易背景材料                                                                                        |
| 基本流程 | 1. 客户经理登录系统，选择待核验的融资申请2. 系统自动识别需核验的场景（合同、发票、物流等）3. 客户经理确认核验范围，提交核验请求4. 系统自动执行核验任务5. 客户经理查看核验结果，对存疑项补充材料 |
| 后置条件 | 核验结果推送至融资审批流程                                                                                           |
| 异常流程 | 数据源不可用 → 触发降级策略，输出部分核验结果                                                                                |

#### 场景二：风控审核员处理存疑案例

| 项目   | 内容                                                                                     |
| ---- | -------------------------------------------------------------------------------------- |
| 角色   | 风控审核员 (R-02)                                                                           |
| 触发条件 | 系统核验结果为"存疑"或"不确定"                                                                      |
| 前置条件 | 核验任务已完成，产生存疑结果                                                                         |
| 基本流程 | 1. 风控审核员查看待处理存疑案例列表2. 系统展示核验详情及风险提示3. 审核员查看原始材料和相关证据4. 审核员做出人工判定（通过/拒绝/需补充材料）5. 录入判定理由 |
| 后置条件 | 判定结果写入核验记录，推送至业务流程                                                                     |
| 异常流程 | 审核员无法判定 → 升级至运营主管                                                                      |

#### 场景三：运营主管配置核验规则

| 项目   | 内容                                                                              |
| ---- | ------------------------------------------------------------------------------- |
| 角色   | 运营主管 (R-03)                                                                     |
| 触发条件 | 业务规则调整、新欺诈模式出现、监管要求变更                                                           |
| 前置条件 | 具有规则配置权限                                                                        |
| 基本流程 | 1. 运营主管进入规则配置模块2. 选择需调整的核验场景3. 新增/修改/禁用核验规则4. 配置规则参数（阈值、权重、时效等）5. 提交规则变更，经审批后生效 |
| 后置条件 | 规则变更生效，影响后续核验任务                                                                 |
| 异常流程 | 规则配置冲突 → 系统提示冲突项，需人工确认                                                          |

#### 场景四：审计人员追溯核验记录

| 项目   | 内容                                                               |
| ---- | ---------------------------------------------------------------- |
| 角色   | 审计/合规人员 (R-05)                                                   |
| 触发条件 | 定期审计、合规检查、争议处理                                                   |
| 前置条件 | 具有审计查询权限                                                         |
| 基本流程 | 1. 审计人员按条件搜索核验记录2. 查看单笔核验全流程记录3. 查看核验快照（原始数据、核验结果、判定依据）4. 导出审计报告 |
| 后置条件 | 审计结论记录归档                                                         |
| 异常流程 | 核验记录不完整 → 标记为审计异常项                                               |

### 5.2 核验模块详细功能描述

#### 5.2.1 贸易合同真实性核验 (F-100系列)

**F-101 合同要素一致性核验**

| 项目        | 内容                                                                                                             |
| --------- | -------------------------------------------------------------------------------------------------------------- |
| **功能描述**  | 对贸易合同的核心要素进行一致性校验，包括合同编号、签约方名称、签约日期、合同金额、标的物描述、交货条款、付款条件等                                                      |
| **核验规则**  | 1. 合同编号格式校验（是否符合标准格式）2. 签约方名称与工商登记信息比对3. 签约日期逻辑校验（不晚于当前日期、符合业务逻辑）4. 合同金额合理性校验（金额范围、数字大小写一致性）5. 标的物描述与合同类型匹配度校验 |
| **输入数据**  | 合同扫描件/电子合同、合同结构化数据（JSON/XML）                                                                                   |
| **输出结果**  | 各要素一致性校验结果（通过/不通过/存疑），不一致项详细说明                                                                                 |
| **数据源依赖** | 工商信息数据库（签约方名称核验）                                                                                               |
| **降级策略**  | 工商信息不可用时，仅进行格式校验和逻辑校验，输出降级标识                                                                                   |

**F-102 签章有效性核验**

| 项目        | 内容                                                                               |
| --------- | -------------------------------------------------------------------------------- |
| **功能描述**  | 对合同上的签章进行有效性核验，包括电子签章和纸质盖章                                                       |
| **核验规则**  | 1. 电子签章：验证数字证书有效性、签章时间戳、签章完整性2. 纸质盖章：与预留印鉴比对（如有）、签章位置合理性校验3. 多方签章完整性校验（各方是否均已签章） |
| **输入数据**  | 合同扫描件（含签章区域）、电子签章数据、预留印鉴样本                                                       |
| **输出结果**  | 签章有效性判定结果，无效签章原因说明                                                               |
| **数据源依赖** | 电子认证服务（CA）、预留印鉴库                                                                 |
| **降级策略**  | 电子认证服务不可用时，标记为"人工核验"                                                             |

**F-103 合同条款合理性核验**

| 项目        | 内容                                                                                                         |
| --------- | ---------------------------------------------------------------------------------------------------------- |
| **功能描述**  | 对合同条款的合理性进行核验，包括合同条款的完整性、关键条款的明确性、是否存在明显不合理条款                                                              |
| **核验规则**  | 1. 必备条款完整性检查（合同金额、标的、交付、付款、违约责任等）2. 关键条款明确性检查（金额、日期、数量等是否明确）3. 行业惯例比对（条款是否符合行业惯例）4. 异常条款检测（如超长账期、异常高额违约金等） |

### 5.3 核验流程引擎 (F-700系列)

#### 5.3.1 核验流程编排 (F-701)

**功能描述**：根据融资申请类型和业务场景，动态编排核验流程，确定需要执行的核验任务及执行顺序。

**设计要点**：

1. **流程模板化**：预定义各场景的核验流程模板，支持参数化配置
2. **动态编排**：基于业务规则动态调整核验流程（如：发票金额超过阈值时增加人工审核节点）
3. **并行执行**：无依赖关系的核验任务并行执行，提升处理效率
4. **条件分支**：支持条件分支逻辑（如：核验不通过则直接阻断，无需继续后续核验）

**流程模板示例**：

```
保理业务核验流程模板：
  1. 贸易合同核验（并行）
     - 合同要素一致性核验
     - 签章有效性核验
     - 合同条款合理性核验
  2. 发票核验（并行）
     - 税局四要素核验
     - 发票查重核验
     - 发票与合同匹配度核验
  3. 确权核验（并行）
     - 确权函真伪核验
     - 确权人身份核实
     - 确权内容一致性核验
  4. 应收账款核验（并行）
     - 账期合理性核验
     - 回款路径验证
     - 历史回款记录核验
  5. 综合判定
     - 汇总各维度核验结果
     - 执行综合判定规则
     - 输出最终核验结果
```

#### 5.3.2 数据源降级策略 (F-702)

**功能描述**：当外部数据源不可用时，自动执行降级策略，确保核验流程可继续执行。

**降级策略定义**：

| 数据源状态          | 降级策略          | 输出标识      |
| -------------- | ------------- | --------- |
| 正常可用           | 正常执行核验        | 无         |
| 暂时不可用（超时<5秒）   | 重试3次后仍失败，执行降级 | 降级-数据源不可用 |
| 长期不可用（接口维护/下线） | 跳过该核验项，执行替代方案 | 降级-跳过     |
| 返回数据不完整        | 使用可用数据执行部分核验  | 降级-部分核验   |
| 数据异常（返回格式错误）   | 标记为数据异常，需人工确认 | 降级-数据异常   |

**降级影响评估**：每次降级执行时，需评估降级对核验结果置信度的影响，并在核验报告中明确标注。

#### 5.3.3 核验时效管理 (F-703)

**功能描述**：管理核验结果的有效期，确保核验结果的时效性。

**时效策略**：

| 策略类型  | 说明                            | 有效期    |
| ----- | ----------------------------- | ------ |
| 固定有效期 | 所有核验结果默认有效期30天                | 30天    |
| 动态调整  | 根据核验置信度动态调整有效期（置信度高延长，置信度低缩短） | 15-60天 |
| 事件驱动  | 特定事件触发重核（详见F-704）             | 即时触发   |

**有效期管理**：

1. 核验结果生成时记录有效期截止时间
2. 融资审批时检查核验结果是否在有效期内
3. 超过有效期的核验结果自动标记为"已过期"，需重新核验
4. 有效期临近（7天）时发送预警通知

#### 5.3.4 事件驱动重核机制 (F-704)

**功能描述**：当交易数据发生变更时，自动触发相关核验任务重核。

**触发事件列表**：

| 事件编号   | 事件类型     | 触发条件       | 重核范围             |
| ------ | -------- | ---------- | ---------------- |
| EVT-01 | 融资金额调整   | 融资金额变更超过阈值 | 合同核验、发票核验、应收账款核验 |
| EVT-02 | 账期修改     | 应收账款到期日变更  | 账期合理性核验          |
| EVT-03 | 核心企业评级变动 | 核心企业信用评级调整 | 确权核验、应收账款核验      |
| EVT-04 | 发票状态变更   | 发票被作废/红冲   | 发票核验             |
| EVT-05 | 合同变更     | 合同条款发生变更   | 合同核验             |
| EVT-06 | 回款账户变更   | 回款账户信息修改   | 回款路径验证           |
| EVT-07 | 定期重核     | 有效期到期前7天   | 全部核验项            |

**重核策略**：

1. 增量重核：仅重核受影响的核验项，不重新执行全部核验
2. 全量重核：当多项变更累积或关键信息变更时，执行全量重核
3. 重核频率控制：同一笔融资申请24小时内重核次数不超过3次

#### 5.3.5 核验结果综合判定 (F-705)

**功能描述**：基于各维度核验结果，按照业务决策机制输出最终核验结论。

**判定结果分类**：

| 结果分类    | 判定条件                  | 业务影响             | 后续处理            |
| ------- | --------------------- | ---------------- | --------------- |
| 通过      | 所有核验项均通过，且无降级项        | 正常进入融资审批流程       | 无               |
| 通过（带降级） | 所有核验项无明确不通过，但有降级核验项   | 正常进入融资审批流程，标注降级项 | 降级项需人工确认        |
| 存疑      | 存在核验结果为"不确定"的项，但无不通过项 | 输出风险提示，转人工决策     | 风控审核员审核         |
| 不通过     | 存在核验结果为"不通过"的项        | 直接阻断业务流程         | 通知客户经理，说明不通过原因 |
| 无法判定    | 关键数据源全部不可用，无法完成核验     | 暂缓流程，需人工介入       | 运营主管确认处理方案      |

**业务决策机制**：

- **硬控制**：核验不通过 => 直接阻断业务流程，不允许继续
- **软控制**：核验存疑/不确定 => 输出风险提示，供人工决策
- **统一策略**：所有供应链金融产品采用统一的核验判定策略

2. 权重类参数（如：各核验项在综合判定中的权重）
3. 开关类参数（如：是否启用某项核验规则）
4. 枚举类参数（如：核验结果判定等级）
5. 时间类参数（如：有效期天数、重核间隔时间）

#### 5.4.3 规则变更审批流程 (F-805)

**功能描述**：对核验规则的变更进行审批管理，确保变更的合规性和可追溯性。

**变更流程**：

1. 运营主管提交规则变更申请
2. 系统自动评估变更影响范围
3. 风控负责人审批（一级审批）
4. 重大变更需合规部门审批（二级审批）
5. 审批通过后，规则在指定时间生效
6. 变更记录写入审计日志

### 5.5 报告与可视化 (F-900系列)

#### 5.5.1 核验结果报告生成 (F-901)

**功能描述**：为每笔核验任务生成完整的核验结果报告。

**报告内容**：

1. 核验任务基本信息（申请编号、融资金额、申请日期等）
2. 各维度核验结果明细（合同、发票、物流、确权、订单、应收）
3. 综合判定结果及业务建议
4. 数据源使用情况及降级标识
5. 核验时间线（各步骤执行时间）
6. 核验依据和证据链
7. 人工审核记录（如有）

**报告格式**：PDF、HTML、JSON（API直接返回）

#### 5.5.2 核验仪表盘 (F-902)

**功能描述**：提供核验业务的实时运营监控仪表盘。

**展示指标**：

1. 今日核验总量及趋势
2. 核验结果分布（通过/存疑/不通过比例）
3. 平均核验处理时间
4. 数据源可用率
5. 待处理存疑案例数量
6. 各场景核验量排行
7. 系统并发处理量

#### 5.5.3 运营统计分析 (F-903)

**功能描述**：提供多维度核验运营数据分析能力。

**分析维度**：

1. 时间维度（日/周/月/季度/年度趋势）
2. 业务维度（按产品类型、业务线分析）
3. 场景维度（按核验场景分析）
4. 数据源维度（按数据源调用量、成功率分析）
5. 结果维度（按核验结果分类分析）
6. 机构维度（按机构/区域分析）

```
+----------------+     +----------------+     +----------------+     +----------------+
| 8. 结果推送      | <-- | 7. 核验结果存储  | <-- | 6. 综合判定      | <-- | 5. 各维度核验汇总 |
+----------------+     +----------------+     +----------------+     +----------------+
```

**详细步骤说明**：

**步骤1：核验请求提交**

1. 客户经理通过业务系统提交核验请求
2. 系统校验请求参数的完整性和合法性
3. 生成核验任务（taskId），状态设置为"待处理"
4. 写入核验任务记录

**步骤2：核验任务分发**

1. 核验任务进入任务队列
2. 任务调度器根据优先级和当前系统负载，从队列中获取任务
3. 分配任务到核验流程引擎处理
4. 更新任务状态为"处理中"

**步骤3：核验流程编排**

1. 核验流程引擎根据业务类型获取对应的核验流程模板
2. 根据业务参数动态调整核验流程（如：无发票时跳过发票核验）
3. 生成核验项列表，确定各核验项的执行顺序和依赖关系
4. 确定可并行执行的核验项

**步骤4：核验任务执行**

1. 按照编排结果执行各核验项
2. 无依赖关系的核验项并行执行
3. 有依赖关系的核验项串行执行
4. 每个核验项执行时：
   a. 检查依赖数据源是否可用
   b. 调用数据源获取核验数据
   c. 执行核验规则
   d. 记录核验结果和证据数据
   e. 更新核验项状态

**步骤5：各维度核验汇总**

1. 汇总所有核验项的执行结果
2. 统计各维度（合同/发票/物流/确权/订单/应收）的核验结果
3. 生成各维度核验详情

**步骤6：综合判定**

1. 执行综合判定规则
2. 判断业务流程阻断条件（硬控制）
3. 判断风险提示条件（软控制）
4. 输出最终核验结果（通过/存疑/不通过/无法判定）

**步骤7：核验结果存储**

1. 更新核验任务结果
2. 记录核验有效期
3. 写入审计日志
4. 更新任务状态为"已完成"

**步骤8：结果推送**

1. 通过回调/消息推送核验结果到业务系统
2. 通知相关用户（客户经理等）
3. 存疑/不通过的结果，推送到待处理列表

### 12.3 验收流程

**第一阶段：开发自测**

- 开发团队完成单元测试和集成测试
- 确保所有功能测试用例通过
- 提交测试报告

**第二阶段：SIT（系统集成测试）**

- 测试团队执行系统集成测试
- 覆盖所有功能验收标准和非功能验收标准
- 提交SIT测试报告

**第三阶段：UAT（用户验收测试）**

- 业务用户（风控审核员、运营主管等）执行验收测试
- 使用真实业务场景进行测试
- 验收通过后签署UAT确认书

**第四阶段：生产验证**

- 生产环境部署后，进行生产验证测试
- 使用真实业务数据（脱敏）进行验证
- 监控系统运行指标，确认满足非功能验收标准
